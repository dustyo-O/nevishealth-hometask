# Consult — nest-backend — backend, contracts, workspace wiring (spec 001)

_Verified 2026-09-21 on this machine (Node v22.23.2, pnpm 10.18.0) with a throwaway workspace in the scratchpad: `packages/contracts` + a Nest app, built, run, curl-ed and tested. Every version below is from `npm view`; every behaviour claim is from a command that ran. Verification log at the end._

## 0. One decision the lead must take first (spec vs. stack)

- **NestJS 12.0.4** (current major, released 2026-08-27; verified `npm view @nestjs/core time`) ships **all core packages as ESM**. Its own CJS scaffold still uses Jest + ts-jest but only via `node --experimental-vm-modules …/jest.js` (`@nestjs/schematics@12.0.4` template `ts/package.json`). **On Node 22 that does not work**: Jest's runtime can `require()` ESM only on Node ≥ 24.9 (jestjs.io/docs/ecmascript-modules, "require of ESM"). Reproduced: both `jest` and `node --experimental-vm-modules jest` fail on `import { Test } from '@nestjs/testing'` with `Must use import to load ES Module … Use Node v24.9+ where Jest supports require(esm) natively`.
- So with **D1 = Node 22**, architecture §1 "NestJS (current major)" and §4 "Jest via Nest CLI + supertest" cannot both hold. Two consistent stacks:
  1. **Recommended: Nest 12 (ESM app) + Vitest 5 + supertest 7** — the Nest team's own default (`ts-esm` template: `vitest run`, `@nestjs/testing` unchanged, no swc plugin needed). Proven end to end here: `tsc --noEmit`, `nest build`, `node dist/main.js`, `nest start`, `vitest run` unit + e2e (6/6) incl. decorator-metadata DI, `vi.spyOn(Logger.prototype,'warn')`, supertest. One test runner for the whole monorepo (web is Vitest anyway). Amend: architecture §4, the `nest-backend` and `testing-expert` briefs ("Jest" → "Vitest").
  2. **Fallback: Nest 11.2.5 (CJS) + Jest 30 + ts-jest 29.4** — the classic path, works on Node 22, but 11 is the previous major (still released 2026-09-15). Amend architecture §1.
- Everything below assumes stack 1; where stack 2 would differ, it says so.

## 1. `packages/contracts` (risk R1)

**Recommend (a): export the TypeScript source, no build step.** `"exports": { ".": "./src/index.ts" }` with `"type": "module"`. Verified for all four consumers: Vite/Vitest transpile linked TS natively; `tsc -p apps/api` under `moduleResolution: nodenext` resolves `exports` → `.ts` and type-checks it (real path is outside `node_modules`, so it is part of the program); `nest build` emits `import … from '@nevis/contracts'` unchanged; **plain `node dist/main.js` loads `packages/contracts/src/index.ts` via Node's built-in type stripping** — default since Node 22.18 (`node -p process.features.typescript` → `strip`), zero warnings in the boot log, HTTP 200. Why: no "build contracts first" in any gate/dev script, no stale `dist`, go-to-definition lands in source, three lanes never wait on each other.
Constraints that make (a) safe: `engines.node ">=22.18 <23"` + `.npmrc engine-strict=true` (older 22.x → `ERR_UNKNOWN_FILE_EXTENSION`); contracts stays one file of *erasable* TS — enforce with `erasableSyntaxOnly: true` (no enums/namespaces/parameter properties); never `--preserve-symlinks` (Node refuses `.ts` under `node_modules`: `ERR_UNSUPPORTED_NODE_MODULES_TYPE_STRIPPING`, reproduced).
**Fallback (b)**: `tsc -p tsconfig.build.json` → `dist/index.js` + `index.d.ts`, `exports: { ".": { types, default } }`, `files: ["dist"]`; also verified (Nest CJS `require()` of the ESM dist works on Node 22 via `require(esm)`, but **Jest on Node 22 cannot**, so stack 2 + (b) needs a CJS or dual build). Cost: `pnpm -r run` topological order does the gate ordering (verified), but `pnpm dev`, editors and fresh clones need a `postinstall`/prebuild. Reject (c) tsconfig `paths`: two resolution mechanisms (tsc/Vite/Node) to keep in sync and `dist/main.js` still needs one at runtime.

`package.json` keys: `name @nevis/contracts`, `private`, `type: module`, `exports`, `sideEffects: false`, `dependencies.zod ^4.6.5`, `devDependencies.typescript 6.0.3` (+ `vitest` if it has its own tests), `scripts { typecheck, lint, test }`. `tsconfig.json` keys: `target ES2023`, `module nodenext`, `moduleResolution nodenext`, `strict`, `noUncheckedIndexedAccess`, `exactOptionalPropertyTypes`, `isolatedModules`, `verbatimModuleSyntax`, `erasableSyntaxOnly`, `noEmit`, `skipLibCheck`, `include ["src"]`. **TypeScript 6.0.3 everywhere** (TS 7.0.2 exists but `ts-jest` peer is `<7`, `typescript-eslint@8.70` peer is `<6.1.0`, Nest CLI 12 depends on `~6.0.2`).

**Schema/type layout — one recursive `TreeNode`, not a union by level.** The spec's wrong-shape rule is *only*: months/company missing, item without `id`/`name`, `values` not exactly 12 numbers; a missing or empty child list is a leaf. A level-typed schema (`Company{branches: Branch[]}` …) would reject documents the spec calls valid (e.g. a branch carrying `channels`) and there is no discriminator field in the data (structure byte-for-byte), so a "discriminated" union is impossible without inventing one; the UI derives level from depth anyway. Write the **interface by hand and annotate the schema with it** — with getter/lazy recursion and `declaration: true` tsc emits `branches: ZodOptional<ZodArray<ZodObject</*elided*/ any>>>`, i.e. `TreeNode.branches` becomes `any[]` for the web app (observed); `export const TreeNodeSchema: z.ZodType<TreeNode> = z.object({ …, branches: z.array(z.lazy(() => TreeNodeSchema)).optional() … })` emits `z.ZodType<TreeNode>` cleanly (observed). Under `exactOptionalPropertyTypes` the interface must read `branches?: TreeNode[] | undefined` (TS2375 otherwise — reproduced both ways).
Exports: `MONTHS` (`as const` tuple `'2024-02'…'2025-01'`), `type Month`, `interface TreeNode { id; name; values: number[]; branches?; employees?; channels? }`, `interface ClientsResponse { months: string[]; company: TreeNode }`, `TreeNodeSchema`, `ClientsResponseSchema` (`months: z.array(z.string().regex(/^\d{4}-(0[1-9]|1[0-2])$/)).length(12)` — one notch stricter than the spec's "months missing"; either amend FR2 with "twelve ISO year-months" or drop `.length/.regex`), `MonthValuesSchema = z.array(z.number()).length(12)` (zod 4 `z.number()` rejects NaN/±Infinity; `z.object` strips unknown keys — fine, tests compare the raw body, not the parsed one). Optional but recommended: `CHILD_KEYS` + `childrenOf(node)` (first present non-empty list in fixed order, `[]` for a leaf) so API check and UI flatten share **one** definition of "children" — a 6-line deviation from "types + one schema", say so in architecture §1 if accepted. `values` stays `number[]` (a 12-tuple type fights `noUncheckedIndexedAccess` and zod infers `number[]`).

## 3. `GET /api/clients` contract

200 `application/json` → `{ "months": ["2024-02", …, "2025-01"], "company": <clients.json verbatim> }` — verified `JSON.stringify(body.company) === JSON.stringify(file)`. `months` = **constant `MONTHS` from contracts**, attached by the repository (a Phase 3 live provider knows its own window; deriving from "configured start month + values length" adds a config key with one legal value). No caching headers, no ETag (out of scope). Errors use Nest's default body — verified: `?fail=1` → 500 `{"message":"Failing on purpose (?fail=1)","error":"Internal Server Error","statusCode":500}`; unknown path → 404 `{"message":"Cannot GET /api/nope","error":"Not Found","statusCode":404}`; no other codes (405 is not emitted by Express 5 — other methods 404). `GET /api/health` → 200 `{ "status": "ok" }`, no `@nestjs/terminus`, switches never apply. Prefix via `setGlobalPrefix('api')` (verified in route log `Mapped {/api/clients, GET}`).

## 4. Dev-only switches

**Interceptor** `DevSwitchesInterceptor` bound with `@UseInterceptors` on `ClientsController` only (health must stay instant for CI readiness); injected `API_CONFIG`. `intercept()` may be async (`Observable | Promise<Observable>` per `nest-interceptor.interface.d.ts`): if `!enabled` → `return next.handle()` **before touching the query** — that is what "ignore entirely" means, and it is why not to parse with `ParseIntPipe` in the controller: the pipe runs in production too and turns `?delay=abc` into a 400 (reproduced). Else `delay = clamp(parseInt(q.delay), 0, maxDelayMs=30000)` (garbage/negative → 0), `await sleep(delay)`, then `if (q.fail === '1') throw new InternalServerErrorException('Failing on purpose (?fail=1)')`. Order gives "wait, then fail" (verified `?delay=1500&fail=1` → 500 in 1.503 s). Gate: `enabled = NODE_ENV !== 'production'`, read once in `loadConfig`; Nest has no build-time env (unlike Vite's `import.meta.env.DEV`), so "production build" **is defined as** `pnpm build && pnpm start:prod` (`NODE_ENV=production`). Not middleware (no DI, awkward to test) nor guard (semantics).

## 5. Data loading

`fs.readFile` at boot in `JsonClientsRepository.onModuleInit` from the injected `CLIENTS_DATA_PATH`, not a build-time `import`: the path is the test seam, `nest-cli.json assets` ships the file, and Phase 3 replaces the provider. Tests: `Test.createTestingModule({ imports: [AppModule] }).overrideProvider(CLIENTS_DATA_PATH).useValue(fixturePath)` (verified) with real files `test/fixtures/broken.json`, `childless.json` (branch without `employees`, adviser without `channels`), `no-branches.json` — matches the spec's "when the service starts with it". Pure functions (`findDiscrepancies`) take the object directly.

## 6. Consistency check

`findDiscrepancies(company)` in `consistency.ts`: depth-first; `kids = childrenOf(node)`; leaf → nothing; else for `i in 0..11` `sum = Σ kids[j].values[i]`, `sum !== node.values[i]` → push `{ path: string[], month: MONTHS[i], expected: sum, actual: node.values[i] }`; recurse. Integers today (verified all 528 values are integers), so `!==`; a tolerance is a Phase 3 concern. `ClientsService.onApplicationBootstrap` (runs after every `onModuleInit`, docs.nestjs.com/fundamentals/lifecycle-events) calls it once and `Logger('ConsistencyCheck').warn(...)` **one line per discrepancy**, plus a final `log` with the count. Emitted line (observed): `WARN [ConsistencyCheck] "Company > Branch 1 > Anna Blackwood" 2024-04: parent 28, children sum 33`. Path = names from the root (ids are UUIDs; duplicates like "New paid" are disambiguated by the path). Pass a string — Nest 12's `ConsoleLogger` treats a trailing object as structured params. Never throws, never mutates (the test deep-equals the input before/after). Shipped data: 44 nodes, 0 discrepancies (verified). **Fixture note:** breaking a *middle* node produces **two** warnings (it vs. its children, its parent vs. it); to get "one warning for that item and month" break a **leaf** (a channel) or the **root**.

## Risks I see

1. **Runner/major decision (§0)** is a spec conflict, not an engineering one; if it stays "Jest", the CI must move to Node 24.9+ or Nest to 11 — pick before slice 0, since it decides `packages/contracts` output format too.
2. **Option (a) rests on Node's type stripping** (default since 22.18, silent on 22.23.2): a developer on 22.12–22.17 gets `ERR_UNKNOWN_FILE_EXTENSION` from `node dist/main.js`; `engine-strict` + `.nvmrc` mitigate; a reviewer may still ask "where is the build?" — one README line.
3. **Decorator metadata is fragile in ESM/strict tooling**: `verbatimModuleSyntax` or an ESLint `consistent-type-imports` autofix turning `ClientsService` into `import type` silently breaks DI (metadata → `Object`) and surfaces only at boot; keep the rule off for `apps/api` and let the e2e boot test guard it.
4. **`.d.ts`/type erosion of the recursive schema** (`any` elision) silently weakens the web lane's types if someone drops the explicit interface/`z.ZodType` annotation; a contracts test that `expectTypeOf<TreeNode['branches']>()` is not `any` catches it.
5. **Fixture semantics vs. the AC wording** "one warning for that item and month": a broken middle node yields two correct warnings; the testing-expert must break a leaf/root or the AC reads as failing.
