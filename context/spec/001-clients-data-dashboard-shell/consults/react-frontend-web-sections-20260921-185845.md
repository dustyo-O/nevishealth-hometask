## 2. Data layer

**`shared/api/http.ts`** — `getJson(url, { signal, timeoutMs = REQUEST_TIMEOUT_MS })`: `fetch(url, { signal: composite, headers: { accept: 'application/json' } })`, then `res.ok ? res.json() : throw HttpError(status)`. Error mapping (exact `detail` strings): fetch rejects with `TypeError` → `NetworkError` "Network error"; `!res.ok` → `HttpError` "Request failed with status 500"; abort with `reason.name === 'TimeoutError'` → `TimeoutError` "Request timed out"; any other abort (TanStack cancelling on unmount) is rethrown untouched; `res.json()` SyntaxError → `UnexpectedShapeError` "Unexpected data shape". Composite signal: prefer a 10-line `withTimeout(signal, ms)` (own `AbortController`, `setTimeout`, abort with `new DOMException('Request timed out', 'TimeoutError')`) over `AbortSignal.any([signal, AbortSignal.timeout(ms)])` — same reason name (verified on Node 22: `AbortSignal.timeout` reason is `DOMException` name `TimeoutError`), but no dependency on `AbortSignal.any` (Safari 17.4+, outside Vite 8's default `baseline-widely-available` target = safari16.4) and it runs under fake timers, which `AbortSignal.timeout` does not.

**`entities/clients/api/fetch-clients.ts`** — `fetchClients({ switches, signal }): Promise<ClientsResponse>`: `getJson(buildClientsUrl(switches), { signal })` → `clientsResponseSchema.safeParse(json)`; on failure `throw new UnexpectedShapeError({ cause: result.error })` (zod issues stay on `cause` for the console; the UI shows only the detail line).

**`shared/api/query-client.ts`** — `createQueryClient(overrides?)` → `new QueryClient({ defaultOptions: { queries: { retry: 1, retryDelay: RETRY_DELAY_MS, staleTime: Infinity, gcTime: Infinity, refetchOnWindowFocus: false, refetchOnReconnect: false, networkMode: 'always', ...overrides } } })`. Option names/types verified in `@tanstack/query-core@5.103.2` `build/modern/hydration-*.d.ts` (`retry?: boolean | number | (failureCount, error) => boolean`, `retryDelay?: number | (failureCount, error) => number`, `staleTime`, `gcTime`, `refetchOnWindowFocus/refetchOnReconnect/refetchOnMount?: boolean | 'always' | fn`, `networkMode?: 'online' | 'always' | 'offlineFirst'`; `queryFn` receives `{ signal, queryKey, client, meta }`). Why app-wide defaults rather than per-query: the policy is the spec's, not the query's, and tests can pass `createQueryClient({ retryDelay: 0 })` to run the error path in milliseconds without fake timers. `networkMode: 'always'` matters: the default `'online'` *pauses* the query (fetchStatus `'paused'`) when `navigator.onLine` is false — skeleton forever instead of the spec's "Network error" panel. `refetchOnReconnect: false` is belt-and-braces (with `staleTime: Infinity` nothing is ever stale) and documents FR5-AC4.

**`entities/clients/queries/clients-query.ts`** — `clientsQueryOptions(switches)` = `queryOptions({ queryKey: ['clients', switches] as const, queryFn: ({ signal }) => fetchClients({ switches, signal }) })` (`queryOptions` is exported by `@tanstack/react-query@5.103.2`, checked in its `index.d.ts`); `useClientsQuery(switches)` = `useQuery(clientsQueryOptions(switches))`. Retry after failure (`refetch()`) re-runs the same fetch cycle including the `retry: 1` policy — so a persisting failure shows the panel again after ~0.5 s + two fast failures (FR4-AC4).

**`entities/clients/model`** — `formatMonth(iso)`: `new Intl.DateTimeFormat('en', { month: 'short', year: 'numeric', timeZone: 'UTC' }).format(new Date(Date.UTC(y, m - 1, 1)))` (UTC on both sides so negative-offset zones never roll to the previous month; verified output `"Feb 2024"`, `"Jan 2025"`). `formatPeriod(months)` → `` `${n} months · ${first} – ${last}` `` with U+00B7 and U+2013 exactly as the spec writes them; `formatBranchCount(company)` → `` `${company.name} · ${n} ${n === 1 ? 'branch' : 'branches'}` `` (spec covers 0/2/3; "1 branch" is my proposal — lead to confirm). Summary derivation lives here, not in the page, because it is data → string and the spec says "computed from the loaded data".

## 3. Page states

View derivation from `useQuery` (important: after an error, `refetch()` keeps `status: 'error'` while `fetchStatus: 'fetching'`, so `isPending`/`isLoading` are *false* during Retry): `view = data ? 'loaded' : isFetching ? 'loading' : 'error'`. The first load and every Retry therefore show the skeleton; `status === 'error' && !isFetching` shows the panel.

Composition (always rendered in this order): `<main>` → `<h1>Clients</h1>` → `<VisuallyHidden as="p" role="status">{view === 'loading' ? 'Loading clients…' : ''}</VisuallyHidden>` → `<div aria-busy={view === 'loading'} className={grid}>` containing either the two `Card`s (children = skeleton compositions or the summary `<p>`) or the `ErrorPanel`. Decisions: the live region is **persistent and polite** (`role="status"`) — a node that exists before the text changes announces reliably, polite because loading is not urgent and must not clobber the page-title announcement; it sits **outside** the `aria-busy` container because assistive tech may suppress content inside a busy region. Skeleton blocks are `<span aria-hidden="true">` with no text; the shimmer is disabled under `prefers-reduced-motion`.

`ErrorPanel` props: `{ message: string; detail: string; onRetry: () => void; retryLabel?: string }` → `<section aria-labelledby={id}><div role="alert"><p id={id}>{message}</p><p>{detail}</p></div><Button type="button" onClick={onRetry}>{retryLabel ?? 'Retry'}</Button></section>`. `role="alert"` on the *text block* only: an alert region should not carry interactive content, and inserting the alert node announces without moving focus (FR4-AC9). No `autoFocus`. One addition for the lead to accept/decline: clicking Retry unmounts the focused button (focus falls to `<body>`); giving `<h1 tabIndex={-1}>` focus on Retry keeps keyboard users placed. `Button`: native `<button>`, `ButtonHTMLAttributes` pass-through, `type` defaults to `"button"`, visible `:focus-visible` ring from tokens. `Card`: `<section aria-label={label} className={cx(styles.card, className)}>`, presentational otherwise. `Skeleton`: `{ className }` only — sizes come from module CSS, never inline styles.

Layout shift: both loading and loaded states render the **same two `Card` shells in the same grid slots**; the slots carry `min-height: var(--card-chart-min-h)` (430px) and `var(--card-table-min-h)` (280px) — the design's heights at 1440, kept as minimums at every width (heights don't overflow at 375). The summary `<p>` reserves `min-height: var(--line-height-body)`. The heading is rendered in all three states. The error panel replaces the cards (spec), so no reservation is needed there. Skeleton ↔ real-widget fidelity is R4 and is fixed in 002/003.

## 4. Dev switches (FR6)

`entities/clients/api/dev-switches.ts`: `readDevSwitches(search: string): DevSwitches` = `import.meta.env.DEV ? pick(new URLSearchParams(search), ['delay', 'fail']) : {}` — the gate is inside this one function, at the branch, not passed as a parameter. Vite's guide "Env Variables and Modes" states `import.meta.env.DEV` is "statically replaced at build time to make tree-shaking effective"; Vite 8's minifier (`build.minify` default `'oxc'`, docs config/build-options) drops the `false ?` branch and the now-unreferenced `pick`. Testability: Vitest does not statically replace `import.meta.env`, and `vi.stubEnv('DEV', false)` is typed `boolean` for `'PROD' | 'DEV' | 'SSR'` (vitest.dev/api/vi.md → `vi.stubEnv`) — the unit test runs the same function under `DEV=true` and `DEV=false` (R5). Proof against the real bundle: the Playwright `prod` project (§8c) opens `vite preview` with `?fail=1&delay=10000` and asserts the captured `/api/clients` request URL has no query — that is FR6-AC4 verbatim.

Retry reuses the switches because the **query key includes them**: the page computes `switches` once (`useState(() => readDevSwitches(window.location.search))`), passes it to `useClientsQuery`, and `refetch()` runs the same `queryFn` with the same key. Re-reading `location` in the fetcher would make Retry drift after a `history.replaceState`, which review finding F3 rejected. The key `['clients', {}]` in production hashes stably.

## Risks I see

1. **TypeScript 7 is `latest` and has no JS API**; anything not pinned to `~6.0.3` (web, api, contracts, root) breaks typescript-eslint/ts-jest at install time, and TS 6's new defaults (`types: []`, `rootDir`, `strict`) silently change what `tsc -b` checks — pin and write every tsconfig key explicitly.
2. **Vitest 5.0.1 is 18 days old**: jest-dom 7.0.1 matcher types vanish (#738) and need the one-line `Matchers<R, T>` shim; if anything else in the RTL/jest-axe chain misbehaves, fall back to `vitest@4.1.11` (same Vite 8 peer) rather than debugging a fresh major in a 6–8 h budget.
3. **ESLint 10 with a two-year-old `jsx-a11y`** works today (verified no removed APIs in `lib/`) but only via a pnpm peer override; if the a11y plugin does break, the replacement is the `oxlint` a11y rule set, not ESLint 9 (EOL).
4. **Timing-based behaviour in tests**: the 21 s hang e2e, the 500 ms retry, and TanStack's `networkMode`/`fetchStatus` semantics (skeleton must key off `isFetching && !data`, not `isPending`) — each is a place where a green test can hide the wrong state; the RTL tests must assert fetch call counts, not just text.
5. **The `prod` Playwright project adds `vite build` (~10 s) to every `pnpm check:web`**; keep it (it is the only honest proof of FR6-AC4) or drop it to a unit test + a README note — the lead decides, not the lane.
