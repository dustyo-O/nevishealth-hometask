### F1: Error deadlines lack a request timeout
- severity: major
- where: functional-spec.md:FR4
- problem: An unreachable service can leave a request pending indefinitely, so the promised error within two seconds cannot be guaranteed. The deadline also conflicts with delayed requests and automatic retries.
- evidence: FR4 promises an error within two seconds of opening the page, but specifies neither a timeout nor retry delay; FR6 permits a three-second response delay.
- fix: Define a request timeout, retry delay, and whether the error deadline starts after the final failed attempt. Specify behaviour when `delay` and `fail` are combined.

### F2: Response envelope changes the architectural contract
- severity: major
- where: functional-spec.md:FR2
- problem: The specification introduces a `{ months, company }` response without reconciling the architecture’s raw-tree contract. Backend and frontend implementations could follow different documents.
- evidence: Architecture §2 says “The API serves it as-is”; FR2 requires “one document containing `months` … and `company`”.
- fix: Explicitly amend the architecture and shared response type/schema to use the envelope, distinguishing it from the unchanged company subtree.

### F3: Removing the failure switch has no defined retry behaviour
- severity: minor
- where: functional-spec.md:FR4, FR6
- problem: Retry recovery after removing `fail=1` is underspecified. Editing the address normally reloads the page, while changing it without navigation may leave Retry using the original request parameters.
- evidence: FR4 requires recovery when “the failure switch [is] removed” and Retry is clicked “without a page reload”.
- fix: Specify that Retry reads the current URL parameters and test removal through the History API, or remove this recovery example and test recovery by restoring the service.

### F4: Empty and sparse payload outcomes are undefined
- severity: minor
- where: functional-spec.md:FR2, FR4, FR5
- problem: The expected shape does not establish whether missing or empty child collections are valid. QA cannot determine whether a childless node should load successfully or produce “Unexpected data shape”.
- evidence: The product definition explicitly supports nodes without children; FR2 describes every hierarchy level, while FR5 only tests three or two branches.
- fix: Define optional versus required child collections, allow childless nodes consistently with the product definition, and specify the summary for zero branches.

### F5: Production switch test imposes an unrelated latency guarantee
- severity: minor
- where: functional-spec.md:FR2, production-build acceptance criterion
- problem: A response taking over one second does not establish that a development switch was honoured. Machine load can fail this criterion even when production correctly ignores both switches.
- evidence: Production must respond “in under 1 second, as if the switches were not there”, with no measurement conditions.
- fix: Test that production returns the normal payload and does not invoke the injected delay or failure behaviour; remove the absolute latency requirement.

## Verdict
SHIP WITH FIXES

Resolve the response contract and failure timing before implementation, and clarify the remaining state tests.
